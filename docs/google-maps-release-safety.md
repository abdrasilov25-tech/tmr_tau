# Google Maps: риски при релизе и что сделать

Часть шагов только в [Google Cloud Console](https://console.cloud.google.com/). В репозитории: ключи не в git, см. `ios/Flutter/Secrets.xcconfig.example`, `android/local.properties.example`.

## 1. Биллинг и «не уйти в минус»

1. Откройте **Billing → Budgets & alerts** в том же Cloud-проекте, где ключ Maps.
2. Создайте **бюджет** (например 20–50 USD/мес на старт) и **уведомления** на 50%, 90%, 100%.
3. Раз в месяц смотрите **Reports** по продукту Maps Platform — не только итог, но и рост по дням.

## 2. Ограничить ключ API (обязательно)

1. **APIs & Services → Credentials** → ваш ключ.
2. **API restrictions**: включите только то, что нужно приложению (минимум: **Maps SDK for Android**, **Maps SDK for iOS**). Остальные Maps API отключите, если не используютесь.
3. **Application restrictions**:
   - **Android**: package name приложения + SHA-1 подписи (debug и release — разные, добавьте оба, если гоняете оба билда).
   - **iOS**: bundle identifier.
4. Отдельный ключ для **разработки** и для **прода** — в проде жёсткие ограничения; на dev можно отдельный проект или ключ с лимитами.

## 3. Репозиторий и утечки

- Никогда не коммитьте строки вида `AIzaSy...`. Android: только `local.properties` (gitignored). iOS: `ios/Flutter/Secrets.xcconfig` (gitignored).
- В CI: workflow **Secret scan (Maps)** — при появлении паттерна ключа в отслеживаемых файлах сборка падает.

## 4. Продуктовые рычаги (уменьшить число сессий с картой)

- Карта только в одном разделе (у вас так и есть — «Рядом»).
- По желанию: не показывать карту неавторизованным или гостевой упрощённый режим — меньше загрузок тайлов.
- При сильном росте: рассмотреть OSM + `flutter_map` как план Б (отдельная задача).

## 5. После инцидента

Если ключ утёк — **rotate**: удалить/отозвать ключ в Console, выпустить новый, обновить только локальные файлы (`local.properties`, `Secrets.xcconfig`), не коммитить.
